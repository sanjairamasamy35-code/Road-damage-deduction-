# Tamil Nadu Road Damage Detection Prototype

This Streamlit app displays Tamil Nadu district boundaries over the OpenStreetMap street and highway basemap. The OSM tile layer includes its standard attribution. The map click tool selects an approximate report location; coordinates may also be entered manually.

## Reports and local data

- Reports persist in `data/road_reports.sqlite`; the app creates the database and `road_reports` table automatically and applies additive, non-destructive migrations.
- New reports start as `Submitted`. Report History offers only the configured next status steps and requires a reason for each change. Changes and their entries in `report_status_history` are committed in one SQLite transaction.
- Lifecycle statuses are `Submitted`, `Pending Validation`, `Validated`, `Assigned`, `Repair Scheduled`, `Repair In Progress`, `Repair Completed â€” Pending Verification`, `Verified and Closed`, `Rejected`, and `Reopened`.
- Legacy `Pending` and `Pending Review` records map to `Pending Validation`. Legacy `Resolved` maps to `Repair Completed â€” Pending Verification`; it is never treated as independently verified. Other existing status values are retained. The migration adds a baseline status-history entry once per existing report and does not delete or move report rows or uploaded photos.
- Moving a report to `Verified and Closed` requires a separate verification note/reference. Uploading the original report photo does not satisfy this requirement.
- Status history records the actor as `Local app operator (unauthenticated)`. The prototype has no verified authentication system; this label is an audit note, not a secure identity or role-based access control.
- Optional JPEG, PNG, or WebP photo evidence is validated and saved in `data/uploads/` (5 MB maximum).
- Map markers are created only from saved report records with valid coordinates. No sample incidents or synthetic road geometry are added.
- The supplied 2021 geoBoundaries file has 34 district polygons and predates later district divisions. The form offers the current canonical district registry; polygon matching only applies where a valid local feature exists.

## Tamil Nadu district registry and boundary coverage

- `data/tamil_nadu_district_registry.json` is the local 38-district registry, retrieved on 2026-10-19. The displayed names follow the official [Tamil Nadu district directory](https://lokbhavan.tn.gov.in/districts-of-tamil-nadu/). Stable IDs use the app namespace `TN-DIST-<UPPERCASE_SLUG>`; these are RoadGuard IDs, not government-issued LGD codes. Name aliases retain common spellings used by older data.
- The current local GeoJSON has **34 valid, uniquely matched district polygons**. The four missing boundary features are **Chengalpattu, Thiruvallur, Thiruvarur, and Thoothukudi**. The app does not synthesize polygons for them; their reports can still be selected manually, but map click matching and coordinate verification are unavailable there.
- Existing geometry is from the project's geoBoundaries India ADM2 extract (boundary year 2021, ODbL 1.0 attribution recorded below). The official [TNGIS portal](https://www.tngis.tn.gov.in/apps.html) states that approval from TNeGA is required for commercial use/applications. The [Survey of India catalog](https://surveyofindia.gov.in/pages/data-catalogue) lists administrative boundary products, but the reviewed catalog does not provide an openly licensed downloadable 38-district file for this app. geoBoundaries' [gbOpen license guidance](https://www.geoboundaries.org/api.html) states CC-BY 4.0, but the current India ADM2 payload and its effective year could not be inspected to verify all 38 Tamil Nadu features. No new boundaries were added, and the 38/38 boundary mismatch is not fixed.
- Registry source records and retrieval date are stored with the registry data. `district_id` was added to SQLite non-destructively. Existing `district` text is retained exactly; only confident aliases are backfilled, and unmatched historical labels remain visible as legacy values. New reports save both the canonical ID and displayed name.
- Coordinate matching validates polygon ring structure, geographic bounds, closure, zero area, ring self-intersections, and hole placement. Only an unambiguous point strictly inside a valid polygon matches. Boundary, overlap, missing coverage, and invalid geometry return no automatic district assignment.

## AI photo analysis (Phase 3)

- The **Report History** details panel can run CPU ONNX inference on that report's saved photo. It shows the original evidence, a separate annotated copy, detections/classes/confidence/boxes, processing duration and the recorded result. It never modifies the original photo or a report's lifecycle status. An empty result is advisory and never rejects a report.
- The implementation follows the upstream [`web/index.html`](https://github.com/VivekVagale/road-hazard/blob/main/web/index.html): RGB planar float input, 640 by 640, aspect-preserving resize with rounded dimensions, centered RGB 114 padding, normalization by 255; output `[1, 8, 8400]`; maximum class score per candidate; 0.25 default confidence threshold; class-wise greedy NMS at IoU 0.45. Coordinates are mapped back through the resize scale and padding. Class order is D00 longitudinal crack, D10 transverse crack, D20 alligator crack, D40 pothole.
- The expected local model is `models/yolo11n.onnx`. The supplied file is 10,607,022 bytes (SHA-256 `a93a8e1735aaf6cd502d13be54684b6335eb8cca1eec270d053e43550531e1f9`). It was loaded with ONNX Runtime 1.31.0 on `CPUExecutionProvider`; the verified interface is input `images` `[1, 3, 640, 640]`, output `output0` `[1, 8, 8400]`. Embedded class metadata lists `longitudinal_crack`, `transverse_crack`, `alligator_crack`, `pothole` in the required D00/D10/D20/D40 order. The app repeats these compatibility checks at startup of each analysis and records a clear error if they fail.
- Results are saved non-destructively in `ai_detections` in the existing SQLite database. Annotated JPEG copies go to `data/annotated/`; source report photos remain in `data/uploads/`. AI records do not transition reports.
- Upstream code is available under the repository's [MIT license](https://github.com/VivekVagale/road-hazard/blob/main/LICENSE). The ONNX model metadata itself declares `AGPL-3.0 License`; the repository README identifies RDD2022 training data as CC BY 4.0 and provides the [dataset citation](https://doi.org/10.6084/m9.figshare.21431547). The local ONNX file's hash has not been compared with a published upstream artifact, so its exact provenance remains unconfirmed. The upstream code license is not a separate grant for model weights or training data. Check the model metadata, weight terms and dataset terms before redistribution.
- The upstream project reports weak performance on rural/unpaved roads and transverse cracks, and notes that speed breakers and debris are outside the listed classes. Those are upstream limitations, not RoadGuard evaluation results. No RoadGuard accuracy evaluation has been performed. The system is an aid for human review, not confirmation that a defect exists or that a report should be rejected.
- CPU inference requires the CPU-compatible `onnxruntime` package in `requirements.txt`; no GPU runtime is used. Start with the existing PowerShell commands above after installing requirements.

## Authority assignment, repairs and verification (Phase 4)

- The **Authority Setup** page stores only locally configured prototype entries. It contains no preloaded government contacts or verified road ownership data. Configured district IDs, road categories, and free-text routing rules are operator-entered hints; they do not establish legal jurisdiction or responsible road ownership. With four district polygons missing and no verified road-ownership source, matching is never treated as automatic jurisdiction resolution.
- The **Operations** page presents open routing cases for manual review and lets a local operator record an authority/team choice, routing rationale, optional due date and any explicitly reported acceptance/decline reference. A newly recorded assignment remains **Awaiting response** until a response is explicitly entered. Declines are recorded and no longer count as active assignments. Every assignment remains in the manual review queue until an operator explicitly records a review outcome; a district-only match never clears it. Assigned officer/team, assignment date, response date and due date are stored where provided. The configured rule text is displayed for human routing but is not automatically evaluated. Acceptance metadata is not authenticated or independently verified.
- Scheduling, work start and completion are separate repair records. Each repair attempt can contain notes, method, materials and its own evidence. Repair-before/after uploads are validated JPEG, PNG or WebP files (5 MB maximum), saved under `data/evidence/` with unique, exclusive filenames. Original report evidence stays under `data/uploads/`, and AI annotations stay under `data/annotated/`.
- The app will not submit repair completion for inspection unless completion notes and a valid repair-after photo are present. An inspector decision must then be explicitly recorded as **Approved**, **Rejected**, or **More Evidence**. Only **Approved** for the latest completed repair attempt can move a case to **Verified and Closed**. Rejected and additional-evidence decisions return the case to **Repair In Progress** for follow-up. This is a local workflow record, not external repair verification.
- Status updates, assignment/repair/verification rows, evidence references, and the existing status-history record are written transactionally where they change together. SQLite migrations add `authorities`, `assignments`, `assignment_history`, `manual_review_queue`, `repair_records`, `report_evidence`, and `verifications`; they do not drop or recreate existing reports, status history, AI detections, or photos. Existing report photos and saved AI annotation paths are backfilled as evidence references only; the files are not copied, moved, or replaced. Actionable existing reports enter the open manual-routing queue until explicitly reviewed.
- Dashboard totals from SQLite include cases awaiting manual authority review. An **overdue job** is an active assignment with a non-null due timestamp earlier than the current UTC time while its report remains Assigned, Repair Scheduled, Repair In Progress, or Repair Completed â€” Pending Verification.
- Actor fields are recorded as local unauthenticated prototype metadata. The app has no verified login, identity assurance, or role-based authorization. A username/role label is not a security control; this workflow is not production authorization.

## Dashboard consistency and demo readiness (Phase 5)

- Dashboard counts and Report History use the same parameterized report query logic. A count button opens Report History with the matching workflow filter; issue-category count buttons open the matching damage type. History filters cover submission date range, canonical/legacy district, damage type, severity, status, configured authority (including no active assignment), the latest AI result, and workflow group. AI outcome refers to the latest recorded inference by timestamp and row order, not to a report validation decision.
- **Total** counts every saved report. **Open** counts every status except Verified and Closed and Rejected. The lifecycle buckets are separate: **Unassigned** means status Submitted, Pending Validation, Validated, Assigned, or Repair Scheduled and no active assignment; **Assigned or scheduled** means status Assigned or Repair Scheduled with an active assignment; **Repair in progress**, **Awaiting verification**, **Verified**, and **Reopened** each count their exact corresponding status. These lifecycle buckets do not overlap. A report with a stale/malformed lifecycle and assignment combination may fall outside a bucket, but remains in Total/Open according to its status.
- **Manual authority review** counts distinct reports with an Open manual-review queue entry. It is deliberately independent of assignment and lifecycle counts; assignment, scheduling, local acceptance metadata, or AI output never resolves the queue. Only an explicit recorded review outcome resolves it. A queue count can therefore overlap another dashboard category.
- **Overdue jobs** counts distinct reports with an active assignment, a non-null due timestamp earlier than current UTC time, and status Assigned, Repair Scheduled, Repair In Progress, or Repair Completed — Pending Verification. It excludes closed/rejected/reopened cases and assignments without a due time.
- **Average submission-to-assignment time** uses each report's earliest recorded assignment timestamp paired with its submission timestamp. **Average repair completion time** uses repair records with both start and completion timestamps. Negative, missing, or unparsable durations are excluded. **Verification failure rate** is (Rejected + More Evidence decisions) divided by all recorded verification decisions; the denominator is decision records, so a report with multiple inspection attempts contributes each attempt. Each metric displays **Unavailable** when no usable records exist. These are prototype database summaries, not independent performance or service-level measurements.
- Dashboard calculations do not edit reports, assignments, AI detections, evidence, or history. AI results remain advisory and do not validate, route, complete, or close a report. Authority entries and routing remain local and unverified. The application has no secure authentication, verified jurisdiction routing, government integration, or notification delivery.
- Report creation uses an additive nullable submission token with a partial unique index. The Streamlit form reuses its token for retry protection, disables resubmission after commit, and allows an explicit new-report action. Existing rows receive NULL and remain unchanged. This prevents the same form submission from creating duplicate report/history/queue rows; it does not attempt to deduplicate distinct reports that happen to describe similar road problems.

## AI evaluation and explainable predictions (Phase 6)

- **Evaluation pending.** The local project does not contain a compatible labeled held-out evaluation split. `test_images/road_sample_01.jpg` has no matching annotation. The root `pothole.png` is not accompanied by labels or split provenance. Photos in `data/uploads/` and `data/annotated/` are report evidence and are excluded from evaluation. No real-model accuracy metric has been produced.
- A suitable public candidate is Road Damage Dataset 2022 (RDD2022), released through CRDDC 2022. The [official dataset record](https://doi.org/10.6084/m9.figshare.21431547.v1) lists CC BY 4.0. The [RoadDamageDetector project](https://github.com/sekilab/RoadDamageDetector) documents JPEG images with Pascal VOC XML annotations for training and images without labels for the official challenge test split. Its four compatible classes are D00, D10, D20, and D40. The dataset publication describes 47,420 images and more than 55,000 damage instances from six countries. The challenge test images do not provide ground-truth annotations, and the reviewed materials do not establish a road-segment or capture-session-separated test split. This project also does not know whether the candidate ONNX model's training data overlaps RDD2022. Therefore the available public information is not enough to claim an unbiased held-out evaluation, and no dataset was downloaded for this phase.
- `road_ai_evaluation.py` is a separate command-line evaluator for a locally supplied, fully labeled Pascal VOC split. It calls the production `road_ai.run_inference()` function; image preprocessing, decoding, coordinate mapping, and class-wise NMS therefore use the existing inference path. It does not connect to SQLite or write under `data/`, `models/`, uploads, or annotations. The output directory must be new/empty and outside those locations and the input split. Missing labels, duplicate image/XML stems, invalid image files, incompatible dimensions, unknown classes, and invalid/out-of-image boxes stop evaluation with an error.
- The protocol reports fixed-threshold precision, recall, and F1 at confidence 0.25 and IoU 0.50. AP uses detections from confidence 0.001 through the same production NMS (IoU 0.45), all-point interpolated precision-envelope area, and IoU thresholds 0.50 through 0.95 in 0.05 increments. mAP values are macro averages over classes with at least one ground-truth object. Per-class output includes D00, D10, D20, and D40, instance/image counts, and an insufficient-example flag for fewer than 10 ground-truth instances. Classes with no ground truth have unavailable recall, F1, and AP; precision is zero if that class has false-positive predictions and otherwise unavailable. Metrics with no valid denominator are represented as `null`, not zero. The failure report labels false positives, missed detections, and spatially overlapping wrong-class predictions; a wrong-class prediction is also counted as a normal false positive and missed ground truth.
- Example for a separately prepared and provenance-documented held-out split (replace paths and provenance with actual values):

  ```powershell
  .\.venv\Scripts\python.exe road_ai_evaluation.py `
    --images-dir "D:\RDD2022\held-out\images" `
    --annotations-dir "D:\RDD2022\held-out\annotations" `
    --output-dir "$env:TEMP\roadguard-evaluation-run-01" `
    --dataset-name "RDD2022" `
    --dataset-version "CRDDC Figshare v1" `
    --dataset-source "https://doi.org/10.6084/m9.figshare.21431547.v1" `
    --dataset-license "CC BY 4.0" `
    --split-name "held-out road-segment split" `
    --split-provenance "Describe the source grouping and how image/segment leakage was prevented"
  ```

  The command writes `metrics.json`, `failure_cases.json`, and `failure_cases.csv`. JSON includes the model file hash/version, embedded class metadata, dataset and annotation manifest hash, source/license/split provenance, evaluation timestamp, environment, thresholds, sample counts, class distribution and metrics. Failure output identifies image, predicted/ground-truth class, confidence, boxes, IoU, and possible class mismatch. Do not call a random image split road-segment-separated unless the dataset provides that grouping and it was actually used.
- Evaluation tooling tests use temporary images/annotations and mocked inference; they test metric and parser behavior, reproducible exports, and isolation. They do not count as model evaluation. Existing real-model tests, if they pass, only establish the behavior their test names cover; a model-loading or inference smoke test is not an accuracy benchmark.
